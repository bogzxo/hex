# Make Hex plans visible and current

When someone types “write a plan”, they should be able to open the Plan tab and see the proposed steps. If they later say “go ahead”, the same rows should show which step is underway, finished or blocked. The agent should also be able to recover its place after a chat resumes.

## What happens today

- In a live Codex chat, `hex_plan_read` returned an empty list. One `hex_plan_update` created three rows. A second call marked one row done and the next one doing. Reading the plan back confirmed the IDs, states and note. Hex already has the core API. Its existing Noon self-test covers redraw, the tab counter, persistence, invalid batches and clearing a plan. [Plan tools](../Hex.Dawn/Agents/DawnScene.McpPlans.cs) · [Noon self-test](../Hex.Dawn/Testing/DawnScene.SelfTest.Noon.cs)
- This session exposed 70 Hex tools. All 70 descriptions included the same general introduction. The plan tool itself says when to use it, but the shared agent startup rules list search, edits, builds and delegation without mentioning plans. The empty Plan tab’s button supplies an explicit tool instruction and a request to wait. A person typing the same intent in ordinary chat misses that cue. [Shared rules](../Hex.Core/Harness/HexAgentProfiles.cs) · [Plan-tab action](../Hex.Dawn/Noon/DawnScene.Noon.Stage.cs)
- The Codex extension turns a completed plan item into a text note. The Claude Code extension formats `TodoWrite` as a checklist note. Hex can recover an older checklist from notes starting with `[ ]`, `[~]` or `[x]`. Once an explicit chat plan exists, the renderer uses it even if a newer checklist note arrives. This explains one way progress can go stale. The frequency across providers has yet to be measured. [Codex adapter](../hex-extensions/codex/extension.hor) · [Claude adapter](../hex-extensions/claude_code/extension.hor) · [Plan selection](../Hex.Core/Agents/HexAgentPlan.cs)

Suggested shared instruction for a chat-bound agent:

> When the user asks for a plan, publish the proposed steps with hex_plan_update and leave future work pending. When carrying out a plan, mark the active step doing. As steps finish or become blocked, update their IDs and mark the next active step in the same call. On resume, use hex_plan_read to recover your place. A request for a plan authorizes planning. Start implementation when the user requests it.

## How to measure adoption

Before changing the prompt, run the same small task on Codex, Claude Code and Antigravity wherever available. Repeat with the proposed guidance on the same model version and settings. Include a typed plan request, the Plan-tab button, a plan-and-execute request, a later “go ahead”, a mid-task blocker, a resume, and a one-question control. Record unavailable cases separately.

Score the user-visible outcome per scenario and provider. Count explicit requests that produced a populated tab, executed phases that showed a transition before the next phase finished, and unrelated turns that caused a plan write or reminder. Record whether each update came from MCP or a native event. Raw tool-call counts alone cannot distinguish a working native integration from a stale checklist. Keep deterministic adapter and UI regressions in the test suite, and report live-agent results as passes over attempts.
